## 4. Campagne GP0.5

### 4.1 Setup

La campagne a utilisé deux environnements Steam réellement distincts sur le même hôte Linux :

```text
A / host
  Steam A
  installation Scrap Mechanic A
  prefix Proton A
  processus jeu A

B / client
  Steam B
  installation Scrap Mechanic B
  prefix Proton B
  processus jeu B
```

Le client B a rejoint le monde Survival de A par le multijoueur Steam.

Cette configuration prouve les frontières entre deux processus/Steam/Proton et le chemin réseau réel du moteur. Elle ne mesure pas les caractéristiques WAN entre deux machines physiques.

## 5. Enseignements réseau

### 5.1 Transport

`SurvivalGame.network` est suffisant pour le MVP observé.

Décision :

```text
SurvivalGame.network
→ TransportService
→ API stable SMML
```

Le backend vanilla reste un détail d'implémentation remplaçable.

### 5.2 Validation

Les tests négatifs prouvent qu'une enveloppe doit être validée avant dispatch :

```text
type/envelope
contractId
contractVersion
payload
```

L'exception volontaire d'un handler a été isolée et un RPC valide a réussi immédiatement après.

### 5.3 Replicated state

`setClientData` fonctionne sur canaux 3 et 4 sur cette build et fournit le dernier état à un client tardif.

Décision : petit état serveur courant seulement. Le numéro de canal n'est pas un contrat public.

### 5.4 Lifecycle client

Un leave/rejoin de B reconstruit le runtime client.

Décision : bootstrap idempotent, services/abonnements recréables, aucun état critique stocké uniquement dans des globals client.

## 6. Enseignements storage

Séquence moteur validée :

```text
absent
→ save schema 1
→ restart
→ load schema 1
→ migrate 1→2
→ save schema 2
→ restart
→ load schema 2
```

La migration 1→2 n'est pas rejouée en session 3.

Décision :

```text
sm.storage
→ StorageService
→ namespace modId
→ schemaVersion
→ migrations idempotentes
```

Écritures rares/coalescées, jamais par tick.

## 7. Restauration et fermeture

Après session 3 :

1. `finish` host a collecté les résultats ;
2. le snapshot `Save` pré-probe a été restauré ;
3. le probe host a été retiré ;
4. `finish` client a collecté puis retiré le probe ;
5. `merge-results` a retourné PASS ;
6. les deux `SurvivalGame.lua` ont été rehashés à la valeur vanilla attendue ;
7. la recherche de fichiers `SMMLProbeNS` n'a listé aucun résidu.

GP0 se termine donc sur un état restauré, pas sur un jeu laissé patché.

## 8. Limites connues

- même machine physique pour A/B : pas de qualification latence/perte/WAN ;
- pas de stress test réseau ;
- pas de serveur dédié officiel qualifié ;
- pas de garantie que canaux 3/4 restent libres sur une autre build ;
- pas encore de Transaction Engine de production avec write-ahead recovery ;
- pas encore de Content Composer de production.

Ces limites n'empêchent pas GP1 ; elles sont soit des capacités futures, soit des chantiers GP1.

## 9. Décisions stabilisées à emporter en GP1

- Survival direct.

- Pas d'édition directe des saves.
- Baseline/fingerprints avant mutation.
